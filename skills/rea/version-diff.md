# 版本对比逆向

## 工作流（漏斗形：先粗后细）

### 1. 工件级对比（入口）

```
compare_artifacts(旧样本, 新样本)   # 结构/资源/签名/打包差异总览
```

先看**有什么变了**（新增资源、so 变了几个、DEX 差多少），决定往哪层钻。

### 2. 函数级对比（原生二进制）

```
compare_functions(旧session, 新session, 范围)   # 匹配函数对，列出变更集
```

输出"新增/删除/修改"的函数清单——**修改的函数就是精读清单**。

### 3. JS 包对比

```
compare_bundles(旧包, 新包)        # 模块级差异
```

### 4. 行为级定位（改动意味着什么）

```
find_changed_behavior(旧, 新)      # 差异落到可观察行为
```

### 5. 精读差异函数

对 compare 清单里的每个修改函数：两侧各 `analyze_function`，并排读，
写清"改了什么逻辑"（条件变化/新增分支/常量更换）。

### 6. 应用级对比

Web/Electron 应用直接用 `compare_application_versions`（一步到位的封装）。

## 任务模板

- **新功能定位**：compare → 新增函数/模块 → build_call_path 找触发入口 →
  静态精读 + 动态观测确认。
- **安全修复确认**：锁定传闻漏洞相关函数名/特征 → compare_functions 看它变没变 →
  变了就 diff 前后逻辑，给出"补丁前可利用、补丁后加了什么检查"的结论。
- **协议变更**：compare → 加密/协议模块在修改集里 → 两侧 analyze →
  动态各抓一组报文对照。

## 证据要求

- 差异清单：compare 工具的原始输出（evidence 引用）；
- 每条"改了什么"的结论：旧函数行为 vs 新函数行为，关键行并排引用；
- 新增功能结论：静态差异 + 动态触发路径双证据。
